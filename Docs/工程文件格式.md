# 工程文件格式（`.pht`）

本文是工程文件的**字段字典**：哪个字段是什么意思、什么单位、谁写它、读到脏值怎么办。
算法怎么算不在这里，见 [相对定向算法](相对定向算法.md) 与 [算法笔记](算法笔记.md)。

> 改 `src/Core/ProjectFile.cs` 里的字段，**必须**同步改本文；反过来也一样。
> 字段名以本文为准，本文以代码为准。

**我该看哪节**

| 你想干的事 | 看这里 |
|---|---|
| 知道一个字段是什么意思、什么单位 | §4–§8 的字段表 |
| 结果存了哪些数、为什么不存表格 | §9 结果入账 |
| 手改文件（加同名点、改点位） | §11 手工编辑 |
| 分清哪些数是输入、哪些是缓存 | §10 真源与派生 |
| 看一个完整的真文件长什么样 | §12 一个真样例 |
| 改了某个模块，动了哪些字段 | §13 谁写谁读 |
| 想知道保存/读取的内部行为（`.tmp`、`.bak`、锁） | 附录 A |

---

## 1 它是什么

`.pht` 是一个 JSON 文件，存的是**索引**：影像的路径、内/外方位、量测的像点、同名点、
解算结果。**不含像素数据**，一个 500 MB 的航片在工程里只占一行路径。

一个工程目录长这样：

```
教学实验_01.pht          工程文件本体
教学实验_01.pht.bak      上一次保存的内容（Save 时自动轮转）
教学实验_01.pht.bak2     上上次
教学实验_01.pht.bak3     上上上次
教学实验_01.pht.lock     保存期间的互斥锁，正常情况下文件不存在
photos/                  影像（可以放在工程目录外，见 external）
```

影像放在哪里都行：工程里记的是**相对工程文件的路径**，整个目录搬走仍然打得开。
放在工程目录之外的，`external` 会写 `true`——那种工程不能整体搬。

## 2 书写约定

| 项 | 约定 | 说明 |
|---|---|---|
| 编码 | UTF-8，**不带 BOM** | 写盘用 `new UTF8Encoding(false)` |
| 缩进 | 2 空格 | `WriteIndented = true` |
| 换行 | 跟平台走（Windows 上是 CRLF） | `System.Text.Json` 的缩进换行取 `Environment.NewLine`；读的时候两种都认 |
| 键名 | camelCase | `JsonNamingPolicy.CamelCase`；中文不转义 |
| 数组 | 空数组写 `[]`，不省略 | 少一层"这个键有没有"的判断 |
| null | 写 `null`，不省略 | 同上；§4–§8 的字段表里类型带 `?` 的就是允许为 null 的 |
| 缺键 | 一律当默认值 | 手写文件可以只写关心的几个键 |

**数字**用 `System.Text.Json` 的最短往返表示（`0.1` 就写 `0.1`，不会写成 `0.10000000000000001`），
读回来与原值逐位相同。所以本文说的"逐位相等"是可以拿来当测试判据的。

**时间**是 ISO 8601 带偏移的 UTC 时刻，例：`"2026-10-28T12:19:08.6849507+00:00"`。

**路径**一律用 `/` 作分隔符，相对 `.pht` 所在目录。`..` 开头表示在工程目录之外。

**单位**（这张表是硬约定，写错不会报错，只会算错）：

| 量 | 单位 | 出现位置 |
|---|---|---|
| 像平面坐标 `x / y / leftX…` | mm，原点像主点，x 向右、y 向上 | `images[].points[].x/y` |
| 像素坐标 `pixelX / pixelY` | 像元，整数，原点左上角，y 向下 | `images[].points[]` |
| 框标坐标 `fiducials[].x/y` | mm，原点像主点，y 向上 | 相机级 |
| 框标量测 `fiducialMarks[].i/j` | 像元，允许小数 | 影像级 |
| 主距 `focalLength` | mm | 相机与影像内方位 |
| 像主点偏移 `x0 / y0` | mm | 内方位 |
| 像元尺寸 `pixelSize` | mm/像元 | 内方位 |
| 地面坐标 `gcps[].x/y/z`、`xs/ys/zs` | m | 控制点与外方位 |
| 角度 `phi / omega / kappa` | **度** | 外方位、相对定向 |
| 上下视差 `q / maxQ`、中误差 `sigma0 / rmsQ` | mm | 相对定向结果 |
| `condition` | 无量纲（λmax/λmin） | 相对定向结果 |

角度存**度**是界面口径（面板上显示的就是度）。送进算法前由 `Core` 转弧度，
`native/` 只认弧度——这层转换只在 `NativeAlgorithms.ToPose()` 一处做。

## 3 版本

`version` 是整数，写盘时一律写当前程序支持的版本。

| 版本 | 变化 |
|---|---|
| 2 | 影像内/外方位、框标、控制点、像点、像对骨架 |
| 3 | 新增 `tiePoints[]`、`images[].points[].boundTiePointId`、`pairs[].relative`（相对定向结果） |
| 4 | 结果入账（§9）：`images[].interior.affine`、`images[].resection`、`pairs[].model`、`pairs[].absolute` |

**读**：接受 `version <= 4` 的任何文件，版本更高的直接拒收并说明原因（
"工程文件版本为 N，高于当前程序支持的 4，请升级程序"）。不加版本号就加字段，
旧程序会把不认识的键悄悄丢掉，再一保存就真没了——所以宁可让旧程序打不开。

**写**：一律写 4。用 v2 程序打开 v3 文件会直接被拒，这是有意的。

v3 文件读进来就是"这些结果块缺失"，语义与"还没解过"完全一样（§9 的块都可以缺席），
**不需要迁移代码**。

**删键不升版本**（2026-11-07）：`models` 已删（原因见[小项与取舍](小项与取舍.md) X-02）。
它从来是空数组，删掉不丢任何数据，所以不值得升到 4——升版本的代价是"旧程序打不开新文件"，
而这里没有任何东西值得付这个代价。旧文件里的 `"models": []` 读的时候当不认识的键忽略（§11 第 5 条）。

## 4 顶层

```json
{
  "version": 4,
  "name": "教学实验_01",
  "lastSelectedId": null,
  "controlPointSource": "gcp/control.rtf",
  "controlPointZoomDirectory": "gcp/zoom",
  "cameras": [ ... ],
  "images": [ ... ],
  "gcps": [ ... ],
  "tiePoints": [ ... ],
  "pairs": [ ... ]
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `version` | int | 见 §3 |
| `name` | string | 工程名。只用于标题栏与"另存为"的默认文件名，**不参与任何计算** |
| `lastSelectedId` | string? | 预留：上次选中的实体 Id。当前程序不写有意义的値，恒为 `null` |
| `controlPointSource` | string? | 控制点文件的相对路径。重开工程时据此重新载入控制点 |
| `controlPointZoomDirectory` | string? | 控制点放大影像目录的相对路径 |
| `cameras` | array | 相机：内方位与框标坐标（§8） |
| `images` | array | 影像：路径 + 内/外方位 + 框标量测 + 像点（§5） |
| `gcps` | array | 地面控制点（§8） |
| `tiePoints` | array | 同名点（§6），v3 起 |
| `pairs` | array | 像对与相对定向结果（§7），v3 起带结果 |

`controlPointSource` / `controlPointZoomDirectory` 只是路径。载入时文件不存在就把
运行时路径置空，**不改文件里的路径**——换个盘挂上就能打开，用不着重录。

## 5 `images[]` —— 影像

```json
{
  "id": "01-156_50mic",
  "path": "photos/01-156_50mic.jpg",
  "external": false,
  "width": 5616,
  "height": 3744,
  "cameraId": "hammer",
  "hasInterior": true,
  "focalLength": 152.72,
  "x0": -0.004,
  "y0": -0.008,
  "pixelSize": 0.04503,
  "status": "Oriented",
  "hasExterior": true,
  "xs": 1000.0, "ys": 2000.0, "zs": 3000.0,
  "phi": -0.5, "omega": 0.3, "kappa": 2.0,
  "fiducialMarks": [ ... ],
  "points": [ ... ]
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 影像号。**工程内唯一**，像点、同名点、像对都靠它指过来 |
| `path` | string | 相对工程文件的路径。内存里的工程（测试用）可以是 `""` |
| `external` | bool | 路径以 `..` 开头（影像在工程目录之外），工程不能整体搬 |
| `width` / `height` | int | 像素尺寸。像素↔像平面换算要用它，**必须准** |
| `cameraId` | string? | 所属相机。空 = 没指定，做不了框标内定向 |
| `hasInterior` | bool | 下面四个数有没有意义 |
| `focalLength` | double | 主距 mm |
| `x0` / `y0` | double | 像主点相对影像中心的偏移 mm |
| `pixelSize` | double | 像元尺寸 mm/像元 |
| `interiorTimeUtc` | string? | 内定向的入账时刻（v4）。参数式与框标法都写 |
| `affine` | object? | 框标仿射六系数（v4，§9.1）。参数式内定向没有，为 `null` |
| `resection` | object? | 后方交会的质量指标（v4，§9.2）。没做过为 `null` |
| `status` | string | `NotProcessed` / `InteriorDone` / `Oriented`。只是显示用的进度，**不参与计算** |
| `hasExterior` | bool | 下面六个数有没有意义 |
| `xs / ys / zs` | double | 摄影中心，m |
| `phi / omega / kappa` | double | 姿态角，度，按 $R = R_\kappa R_\omega R_\phi$ 分解 |
| `fiducialMarks` | array | 本片量到的框标（§5.1） |
| `points` | array | 本片上量测的像点（§5.2） |

`hasInterior` / `hasExterior` 是**闸门**：为 `false` 时后面那几个数一律写 0、读的时候
必须整块忽略。为什么不干脆把对象省掉：省掉的话每个读的地方都要判断"这个键在不在"，
而 `hasX` 只有一处判断，写错了 `IsValid` 会兜住。

> `status` 与实际数据可能不一致（手改文件就会），所以**任何算法都不许看 `status`**，
> 一律看 `hasInterior` / `hasExterior`。这条是踩过坑的：界面显示"已定向"但外方位是空的。

### 5.1 `fiducialMarks[]` —— 框标量测

```json
{ "id": 1, "i": 128.5, "j": 141.2 }
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | int | 框标编号，对应 `cameras[].fiducials[].id` |
| `i` / `j` | double | 量到的像元坐标，**允许小数**（放大镜下取点不是整数） |

一个框标在一张片上最多一个量测。框标的**理论坐标**存在相机上，不在影像上——同一台
相机换张片，框标坐标不变（ADR-13）。

### 5.2 `points[]` —— 像点

```json
{
  "id": "P01",
  "pixelX": 1032,
  "pixelY": 882,
  "x": -79.97328,
  "y": 44.5797,
  "boundGcpId": null,
  "boundTiePointId": "T01",
  "residualMm": null
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 像点号。**只在本片内唯一**（两张片都可能有 `P01`） |
| `pixelX` / `pixelY` | int | 像素坐标，取点时就这么存 |
| `x` / `y` | double | 像平面坐标 mm。内定向做完后由像素换算，可能与像素不严格对应（换了内定向就会变） |
| `boundGcpId` | string? | 绑到哪个控制点 |
| `boundTiePointId` | string? | 绑到哪个同名点，v3 起 |
| `residualMm` | double? | 解算后回填的像点残差 mm（后方交会写这个，二维残差的模） |

三条规矩：

1. **一个像点最多绑一处**：要么控制点、要么同名点。两个都写属于脏数据，读的时候保留
   控制点、丢掉同名点那一侧，并记一条警告（见附录 A.2）。
2. `x / y` **不是**真值来源。算法要用像平面坐标时一律**由 `pixelX/pixelY` 现算**——
   内定向可能是点完像点之后才做的，那时存的 `x/y` 是没意义的默认值。
3. 同名点的上下视差 `q` **不**写在这里，写在 `tiePoints[].q`。一个点对只有一个 `q`，
   写两遍迟早会出现两个不一样的值。

## 6 `tiePoints[]` —— 同名点

```json
{ "id": "T01", "q": 0.0137, "rejected": false }
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 点号，工程内唯一，形如 `T01` |
| `q` | double? | 上下视差 mm。**按点对**算的，解过才有值 |
| `rejected` | bool | 上一次相对定向把它判成粗差、没参与解算 |

**成员不在这里**。一个同名点由哪些像点组成，看像点一侧的 `boundTiePointId`：

```jsonc
"images": [
  { "id": "IMG_L", "points": [ { "id": "P01", "boundTiePointId": "T01" } ] },
  { "id": "IMG_R", "points": [ { "id": "P01", "boundTiePointId": "T01" } ] }
]
```

上面这两处说明 `T01` 是 `IMG_L` 的 `P01` 与 `IMG_R` 的 `P01` 这一对。为什么只写一处：
两处都写就是两份真相，删一个像点、另一处还留着它，这种文件没有救。读的时候
**以像点为准**，`tiePoints[]` 只提供 `q` 与 `rejected`。

`q` 与 `rejected` 是"上次解算的产物"，不是输入。删掉某个成员点、或者改了点位，
它们就过期了——所以重新解算时整批重写，被跳过的点会把 `q` 清成 `null`。

## 7 `pairs[]` —— 像对与相对定向结果

```json
{
  "id": "PR01",
  "left": "IMG_L",
  "right": "IMG_R",
  "relative": {
    "reference": "IMG_L",
    "bx": 0.034709961387340116,
    "by": 0.9993781077959457,
    "bz": -0.0062141965437699535,
    "phi": 0.057884560194886026,
    "omega": -0.1611407412521495,
    "kappa": 0.3880143666967849,
    "gauge": 1,
    "iterations": 4,
    "usedCount": 12,
    "rejectedCount": 0,
    "focalLength": 152.72,
    "sigma0": 0.019462717327891472,
    "rmsQ": 0.012592502255925765,
    "maxQ": 0.02779950478921497,
    "condition": 2147.272842748558,
    "timeUtc": "2026-10-28T12:19:08.6849507+00:00"
  }
}
```

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | string | 像对号，形如 `PR01` |
| `left` / `right` | string | 左右影像号。左右**对调仍算同一个像对**，不会重复建 |
| `relative` | object? | 相对定向结果。没解过就是 `null`（整个键还在，值是 null） |
| `model` | object? | 模型交会的成果（v4，§9.3）。没做过为 `null` |
| `absolute` | object? | 绝对定向的成果（v4，§9.4）。没做过为 `null` |

`relative` 里：

| 字段 | 类型 | 含义 |
|---|---|---|
| `reference` | string | **基准片**：辅助系的原点在它的摄影中心、三轴与它平行。它可能不是 `left`——用户把两张片对调过解算时，元素属于另一侧 |
| `bx / by / bz` | double | 单位基线方向，$\lvert\mathbf b\rvert = 1$，像空间辅助系 |
| `phi / omega / kappa` | double | 右片相对基准片的三个角，度 |
| `gauge` | int | 实际冻结的基线分量：`0` = $b_x$、`1` = $b_y$、`2` = $b_z$ |
| `iterations` | int | 迭代轮数 |
| `usedCount` | int | 参与解算的点对数（剔除粗差之后） |
| `rejectedCount` | int | 被判为粗差剔掉的点对数 |
| `focalLength` | double | 解算时用的焦距 mm。重开工程据此核对内定向有没有被改过 |
| `sigma0` | double | 单位权中误差 mm |
| `rmsQ` | double | 上下视差中误差 mm。**这就是这一步的验收指标** |
| `maxQ` | double | $\max\lvert q\rvert$，mm |
| `condition` | double | 法方程条件数 $\lambda_{\max}/\lambda_{\min}$ |
| `timeUtc` | string | 解算时刻 |

三件事必须记住：

1. **模型比例尺是自由的**。$\mathbf b$ 被规准成单位长度，模型坐标不是米制，
   要等绝对定向的 $\lambda$ 把它拉回来。别拿模型坐标当米用。
2. **教材式的 $b_y, b_z$ 不存**。教材把基线写成 $(1, b_y, b_z)$，那是按 $b_x$ 归一；
   旁向像对的 $b_x \approx 0$，那样写会除零。要看教材口径，由 $\mathbf b$ 现算
   $b_y/b_x$、$b_z/b_x$（`RelativeOrientation.TextbookBy/TextbookBz`，$b_x$ 太小时给 NaN）。
3. `gauge != 0` 说明这次冻结的不是 $b_x$，也就是"基线主要不在航向"——旁向重叠的像对
   本来就是这样，不是错。

像对是**第一次解算时自动建**的。只把两张片放进左右窗、没解算，工程里不会多出一个像对。

## 8 `cameras[]` 与 `gcps[]`

### 8.1 相机

```json
{
  "id": "hammer",
  "focalLength": 152.72,
  "x0": -0.004,
  "y0": -0.008,
  "fiducials": [ { "id": 1, "x": 106.003, "y": 106.003 }, ... ]
}
```

| 字段 | 含义 |
|---|---|
| `id` | 相机号。影像的 `cameraId` 指过来 |
| `focalLength` / `x0` / `y0` | 检校得到的内方位。**注意**：真正参与计算的是 `images[].focalLength` 那一份，相机上的这份是"标称值"，用来对照与重录 |
| `fiducials[].id` | 框标编号，与 `fiducialMarks[].id` 配对 |
| `fiducials[].x/y` | 框标理论坐标 mm，原点像主点、y 向上 |

少于 4 个框标做不了仿射内定向（4 个才有 0 个多余观测，5 个起才有残差）。

### 8.2 控制点

```json
{ "id": "6157", "x": 5000.123, "y": 4000.456, "z": 120.789, "type": "Planimetric" }
```

| 字段 | 含义 |
|---|---|
| `id` | 点号，来自控制点文件 |
| `x / y / z` | 地面坐标 m。**轴序由数据决定**（见下） |
| `type` | `Planimetric` 平高 / `Elevation` 高程 / `CheckPoint` 检查点 |

轴序不写盘：`X 东 Y 北`（右手系）还是 `X 北 Y 东`（左手系）是从观测数据反推出来的结论，
不是输入。后方交会解算时判一次（三点叉乘），判出来只用于显示换算，**不落文件**。
所以换个软件打开，控制点还是原样那三个数。

检查点 `CheckPoint` 不参与解算，只用来评精度。

## 9 结果入账

每一步解出来的东西写在哪、写多少，这一节说了算。三条总则：

1. **只有被接受的才写。** 解算是算法的事，入账是操作员的判决：结果窗口里按「接受」才落进
   `.pht`，按「不采纳」（或直接关窗）就不写，日志留一行。所以**文件里出现的结果块，一定是有人
   点头过的**，不会留下"上次随手试了一下"的残留。
2. **只存数字，不存表格。** 元素表与残差表是界面排出来的；文件里存参数与残差数值。行宽、小数位、
   单位写在界面里——存渲染结果等于把排版钉进数据，改个格式就得升版本。
3. **能由「观测 + 参数」确定性算出来的，不存。** 框标逐点残差、GSD、$H/B$、绝对定向后的地面坐标
   都是这类；存的是参数加少数几个标量（$\sigma_0$、中误差、条件数）。

**入账带依赖**：接受一份结果时，它依赖的、还没入账的前置会一并入账（日志记一行
「随附入账：相对定向 · PR01」）。否则会出现"文件里有七参数、没有相对定向"这种自相矛盾的工程。

> 四个结果块都挂在**对象**上（`images[]` / `pairs[]`），不另建 `solutions[]` 总表：删掉一张影像或
> 一个像对，它的结果跟着消失，不用写"悬空引用"的清理逻辑——那类清理在 `tiePoints` 上已经不便宜了。

### 9.1 `images[]` 的内定向字段 —— 内定向

内定向的四个数从 v2 起就平铺在影像对象上（`hasInterior / focalLength / x0 / y0 / pixelSize`），
v4 只加两个键，不改结构：

```json
{
  "id": "foto_06_0614",
  "hasInterior": true, "focalLength": 100.5, "x0": 0.0, "y0": 0.12, "pixelSize": 0.006,
  "interiorTimeUtc": "2026-11-07T13:20:11.1234567+00:00",
  "affine": { "a0": 115.25, "a1": -2.1e-06, "a2": -0.045029,
              "b0": 115.23, "b1": -0.045028, "b2": 1.76e-06 }
}
```

参数式内定向直接填那四个数；框标法由六系数反算出它们。`affine` 是**六系数本身**——
反算出的等效 f/x0/y0 **推不回**旋转与倾斜，没有它，重开工程只能看到"等效内参"，复核时对不上。
`affine` 缺席 = 参数式内定向（或 v3 文件）。

### 9.2 `images[].resection` —— 后方交会质量

```json
"resection": {
  "sigma0": 0.0267, "iterations": 4, "usedCount": 6, "rejectedCount": 0,
  "condition": 1834.2,
  "paramSd": [0.0031, 0.0029, 0.0087, 4.1e-05, 4.0e-05, 4.2e-05],
  "timeUtc": "..."
}
```

| 字段 | 单位 | 含义 |
|---|---|---|
| `sigma0` | mm | 单位权中误差 |
| `paramSd` | m / rad | 六个外方位元素的参数中误差（协因数阵对角元开方），顺序 `Xs Ys Zs φ ω κ` |
| `condition` | 无量纲 | 法方程条件数 $\lambda_{\max}/\lambda_{\min}$ |
| `iterations` / `usedCount` / `rejectedCount` | 个 | 迭代轮数、参与点数、被剔除的点数 |

外方位本身仍在 `images[]` 的 `hasExterior / xs…kappa`（v2 起就有）。这一块补的是**这次解的质量指标**：
没有它，重开工程只剩六个参数，$\sigma_0$ 与条件数再也拿不回来——重解会有另一份，且可能不一样。

### 9.3 `pairs[].model` —— 模型交会

```json
"model": {
  "points": [ { "gcpId": "14P1", "x": -0.4601, "y": 0.2218, "z": 0.0042, "angleDeg": 63.1 } ],
  "timeUtc": "..."
}
```

模型坐标是**自由比例尺**（基线长为 1），`x/y/z` 无量纲；`angleDeg` 是两条视线的交会角。
屏幕上的模型点表就是这一块排出来的。

### 9.4 `pairs[].absolute` —— 绝对定向

```json
"absolute": {
  "lambda": 570.695, "phi": -0.41, "omega": 0.27, "kappa": 2.11,
  "dx": 1032.4, "dy": -880.1, "dz": 120.6,
  "groundOrder": "EastNorth",
  "sigma0": 1.6003, "gsd": 0.3019, "hbRatio": 8.860,
  "points": [ { "gcpId": "14P1", "dxy": 0.83, "dz": 0.51, "check": false } ],
  "timeUtc": "..."
}
```

| 字段 | 单位 | 含义 |
|---|---|---|
| `lambda` | 无量纲 | 尺度（模型 → 地面） |
| `phi / omega / kappa` | 度 | 三个旋转角，与界面、`pairs[].relative` 同口径 |
| `dx / dy / dz` | m | 平移 |
| `groundOrder` | 枚举 | **解算时判出的地面轴序**（`EastNorth` / `NorthEast`）。必须存：逐点不符值是在这个口径下算的，重判若得另一个答案，残差会被按错误方向读 |
| `sigma0` | m | 单位权中误差 |
| `gsd` | m/像元 | 地面采样间隔 $\lambda\lvert Z_{\text{model}}\rvert\delta/f$ |
| `hbRatio` | 无量纲 | $H/B$，即深度放大的倍数 |
| `points[].dxy` | m | 该点不符值的平面合量 $\sqrt{\Delta x^2+\Delta y^2}$ |
| `points[].dz` | m | 该点不符值的高程分量 |
| `points[].check` | bool | 是否检查点（检查点不参与解算，只评精度） |

### 9.5 观测指纹 `obsHash`

每个结果块可以带一个 `obsHash`：把该结果**依赖的观测**（点号、地面坐标、像点像素、内参）规范化后
取 FNV-1a 64 位哈希。打开工程时重算一遍，不一致就在结果窗口标「观测已变，这份结果是旧的」。

它治的是"结果存下来了、观测后来改了"这个隐患：不重解，文件里的数就与观测对不上，而且
**没有任何东西能发现**。有了哈希，"对不对得上"从记忆问题变成可判断的事实。`obsHash` 缺席
（v4 之前、或手写文件不写）就跳过比对，不报错也不警告。

### 9.6 谁在什么时候写

| 谁 | 什么时候 | 写什么 |
|---|---|---|
| 结果窗口的「接受」 | 操作员点头 | 该份结果 + 尚未入账的前置 |
| `ProjectFile.Save` | 保存工程 | 内存里已有的结果块，一个不落 |
| 任何任务 | **从不** | 任务只算、只返回；写工程是"接受"这一步的事 |

**收敛是算法的判断，入账是操作员的判断。** 两条闸门各管一段：校验闸门（VL）管"这份结果能不能用"，
它决定「接受」是可按还是禁用；「接受」管"要不要把它记下来"。两者不能合并——解出来了但你不想要，
和解不出来，是两件事。

## 10 真源与派生

文件里有两种东西：**输入**（人给的、算不出来）和**派生**（程序算出来的缓存）。
分清这两类，才知道手改时该动谁。

| 数据 | 谁是准的 | 派生 / 恢复方式 | 手改安全吗 |
|---|---|---|---|
| 影像路径、宽高 | `images[].path/width/height` | — | 安全；路径拼错只是警告（附录 A.2） |
| 内方位 | `hasInterior` + `focalLength/x0/y0/pixelSize` | — | 安全，但改了要重解依赖它的解算 |
| 外方位 | `hasExterior` + `xs…kappa` | 也可由后方交会重解 | 安全，解算会覆盖 |
| 像点像素 | `points[].pixelX/pixelY` | — | **改这里**，它是像点的唯一真源 |
| 像点像平面 | `points[].x/y` | 由像素与内方位现算 | **别手改**，下次解算会覆盖 |
| 同名点归属 | `points[].boundTiePointId` | — | 改它等于改配对，两侧必须一致 |
| 上下视差 | `tiePoints[].q`、`rejected` | 上次解算的产物，重解整批重写 | 改了也无害，会被覆盖 |
| 相对定向元素 | `pairs[].relative` | 重解相对定向 | 安全 |
| 地面控制点 | `gcps[]` | — | 安全 |
| 像点残差 | `points[].residualMm` | 解算后回填 | 改了也无害，会被覆盖 |
| 内定向六系数 | `interior.affine` | 重解内定向 | 安全，但改了就与 `focalLength/x0/y0` 不再一致 |
| 后方交会质量 | `images[].resection` | 重解后方交会 | 安全 |
| 模型坐标 | `pairs[].model` | 重解模型交会 | 安全 |
| 七参数与不符值 | `pairs[].absolute` | 重解绝对定向 | 安全 |
| 观测指纹 | 各块的 `obsHash` | 随结果一起写 | **别手改**：它只用来判断"结果还对不对" |

一条总规则：**派生值永远由输入重算**。手改 `x/y`、`q`、`residualMm` 不会报错，
只会被下一次解算悄悄盖掉——这正是"改了没生效"的最常见原因。

### 10.1 不写盘的东西

有些字段在内存里天天用，但**故意不存**。写盘前过一遍这张表，能省掉很多"为什么打不开"。

| 内存字段 | 为什么不存 | 重开时怎么恢复 |
|---|---|---|
| `ImageItem.FullPath` | 绝对路径换台机器就废了 | 由 `path` + 工程目录现算 |
| `ImageItem.FileState` | 运行时检测结果 | 打开时 `File.Exists` 重新探 |
| `ImageItem.GroundOrder` | 单张影像上没有"轴序"这回事，它是解算的结论 | 判定的结果记在 `pairs[].absolute.groundOrder`（§9.4）；重解会重判 |
| `Project.LoadWarnings` | 本次打开的诊断信息 | 无所谓，下次打开重新生成 |
| `Project.ControlPointSourceFullPath` | 绝对路径 | 由相对路径现算 |
| 界面状态（当前模块、选中行、缩放） | 不是数据 | 不恢复，回默认值 |

**结果进工程，但不是"观测的实时镜像"**：四个结果块（§9）记的是**某一次被接受的解**，不是由观测
现算出来的值。所以观测改了、结果块不会自己变——`obsHash` 就是为这件事留的（§9.5）：对不上时界面
标「观测已变」。要更新，重解一次并接受。

**进工程的只有"每个对象一份"的结果块**：成千上万的同名点仍在 `tiePoints[]` 与像点上，稠密点云
（$10^6$–$10^7$）永远不进 `.pht`——那会让它从"能 diff、能手改的索引文件"变成半个点云文件
（见[小项与取舍 §2.1](小项与取舍.md)）。这和界面上把结果放在哪儿无关（ADR-25 之后是独立窗口）。

**`pixelX/pixelY` 写成整数不是省略**：量化发生在 C ABI 边界——`ImagePixel(int I, int J)` 是整条链的像元口径，
`Coordinates.cs:100` 在那里做唯一一次 `Math.Round`，往后都是整数。均匀量化 $0.5/\sqrt3\approx0.29$ px，
比手工取点还小一档，所以不改（X-06）。

## 11 手工编辑

改 `.pht` 是合法的，几个约束记住就行：

1. 加一对同名点：在两个影像的 `points[]` 里各给一个像点写上同一个 `"boundTiePointId"`，
   再在顶层 `tiePoints[]` 里加一条 `{ "id": "T01" }`（`q` 可以先不写）。
   只写像点那一侧也能读进来，会被补建（附录 A.2）。
2. 删同名点：删掉两个像点上的 `boundTiePointId`（或删掉那两个像点），再删掉
   `tiePoints[]` 里那一条。只删一半会被补建回来。
3. 改点位：只改 `pixelX/pixelY`，**别手改 `x/y`**——算法统一由像素现算，`x/y` 只是记录。
4. 改完 `pairs[].relative` 不会影响任何东西，除非界面直接显示它；要重算请重新解一次。
5. 别动 `version`。想试点什么都不影响的字段，随便加个键，读的时候会被忽略。
   唯一的例外是废弃的 `models`：非空时会警告一句（附录 A.2），因为那里面是手写的东西。

## 13 谁写谁读

改了哪个模块，对照这张表确定动了哪些字段（**表里只写数据关系，不写实现进度**——进度看[路线图](路线图.md)）：

| 模块 | 写 | 读 |
|---|---|---|
| 载入影像 | `images[].id/path/width/height` | — |
| 内定向（参数式） | `images[].hasInterior/focalLength/x0/y0/pixelSize`、`interior.timeUtc` | — |
| 内定向（框标） | 同上 + `interior.affine`（六系数）、`fiducialMarks[]` | `cameras[].fiducials` |
| 后方交会前刺点 | `images[].points[]`（`boundGcpId`） | `gcps[]` |
| 后方交会 | `images[].hasExterior/xs…kappa`、`images[].resection`、`points[].residualMm`、`status` | 上面两行 |
| 前方交会 | 不写（只算：它出的是单次临时点，要成成果得先升级成控制点或同名点） | `hasInterior`、`hasExterior` |
| 相对定向 | `tiePoints[]`、`points[].boundTiePointId`、`pairs[]`、`pairs[].relative`、`tiePoints[].q/rejected` | `images[].hasInterior` |
| 模型交会 | `pairs[].model`（接受时） | `pairs[].relative`、`images[].points[].boundGcpId` |
| 绝对定向 | `pairs[].absolute`（接受时） | `pairs[].relative`、`gcps[]`、`images[].points[].boundGcpId` |
| 报告 | — | 全部（只读**已入账**的结果） |

**只有前方交会不写**：它出的是"这一次点的这一个点"，既不属于哪个对象，也不是下一步的输入。

其余步骤的成果都落盘，但**都过"接受"这一关**（§9）：解出来的东西先进会话级的结果窗口，
操作员按「接受」才写进工程；不采纳就是没发生过（日志留一行）。所以"文件里的结果"永远等于
"操作员认可的结果"，不会出现"上次随手试了一下"的残留。

**入账带依赖**：接受绝对定向时，它用到的相对定向若还没入账，会一并入账——否则文件里会出现
"有七参数、没有相对定向"这种自相矛盾的工程。

重开工程后，已入账的结果直接出现在结果窗口里，不用重算；`obsHash` 对不上时标「观测已变」。

## 附录 A 写入与读取（实现行为）

### A.1 保存：临时文件 → 轮转备份 → 替换

```
写 xxx.pht.tmp  →  把 .bak 抄成 .bak2/.bak3  →  File.Replace(tmp, xxx.pht, bak)
```

崩溃点在哪都不至于留下半个工程：`File.Replace` 是原子替换，最坏情况是 `.tmp` 里躺着
一份没写进去的新内容，原文件完好。所以**看到 `.pht.tmp` 不用慌**，删掉即可。

保存期间会持有 `xxx.pht.lock`（`FileShare.None` + 关闭时自动删）。另一个进程正在编辑
同一个工程时，第二个会直接报错："该工程正在被另一个进程编辑，请先在那边保存并关闭。"

### A.2 读取：能读就读，读不了的东西必须说出来

`ProjectFile.Load` 不抛"格式错误"这种一句话，它尽量把能救的救回来，然后通过
`Project.LoadWarnings` 交出一串人话。界面在打开工程后把它们显示在诊断栏。

| 情况 | 处理 |
|---|---|
| `version` 比程序新 | 直接拒收，说明原因 |
| `tiePoints` 里某条没有 `id` | 忽略这一条，警告 |
| 同一个点号在 `tiePoints` 里出现多次 | 只留第一条，警告 |
| 像点引用了表里没有的点号 | **补建**一个同名点（手写的文件常常只写像点那一侧），警告 |
| 同名点没有任何像点引用 | 丢掉，警告 |
| 像点同时绑了控制点与同名点 | 保留控制点，丢掉同名点那一侧，警告 |
| 像对的左片或右片不在工程里 | 不动它，警告（可能只是换了目录、路径拼错） |
| 像对左右片是同一张 | 不动它，警告 |
| `models` 段非空（已废弃的键） | 忽略，警告"这段被忽略、下次保存就没了"。空数组不吭声——那是我们自己以前写出来的常态 |

一条原则：**不确定就保留 + 说出来**，不要静默修正。静默修正的文件再一保存，
用户就永远不知道少了什么。
