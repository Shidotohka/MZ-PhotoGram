# 计算接口：C# 与 C++ 的边界

> 这份文档原本是[界面设计规范](界面设计规范.md)的第 8 节。2026-11-07 拆分：
> 界面规范只讲界面，这里只讲**哪段代码归哪边、ABI 怎么定、错了谁兜底**。
>
> 相关：工程文件格式见[工程文件格式](工程文件格式.md)，验收判据见[路线图 §6](路线图.md)。

## 1 三层职责

**算法层（C++，`native/`）只做纯计算。** 它假设收到的数据已经是干净的：数学右手系（$X$ 东、$Y$ 北、$Z$ 上）、单位统一（像平面 mm、地面 m、角度弧度）、点号已经对齐。它的任务是解共线方程、构建旋转矩阵、迭代求外方位元素、给出 $\sigma_0$ 与协方差。

底层算法里**不许有针对特定数据源的补丁**：不判轴序、不猜文件格式、不读盘、不统一单位。共线方程解算函数里不该出现 `if (isMirrored) swap(x, y);` 这种分支。

**逻辑层（C#，`src/Core`）负责数据适配与流程控制。** 读文件、认格式（测量学的 RTF / 通用 CSV）、统一单位、**判地面轴序并换轴**、绑定点号、调用 DLL、把结果过闸门、写回模型——这些都是「这份数据长什么样」的知识，与共线方程无关。

**界面层（C#，`src/App`）只画不算。** 布局、交互、把 `Core` 的结果摆出来。光标处的像平面读数也调 `Core` 的同一个换算函数，不自己算一遍。

判定归属只需问一句：

> **这段代码需不需要知道「这份数据来自哪种坐标系、哪个单位、哪家单位给的」？**
>
> 需要 → C#；不需要 → C++。

| 要做的事 | 归属 | 实现 |
|---|---|---|
| 共线方程、法方程、迭代、投影 | C++ | `pgm_resection` / `pgm_project_point` |
| $\sigma_0$、条件数、协方差、残差 | C++ | 同上 |
| 判「这个解要不要接受」 | C# | 约束闸门，见[路线图 §6](路线图.md) |
| 地面轴序、手性、换轴 | C# | `DetectGroundOrder` / `GroundAxes.ToMathFrame` |
| 单位、点号、文件格式、缺省值 | C# | `ControlPointFile` / `CameraFile` |
| 像素 ↔ 像平面换算 | C# | `CoordinateConverter`（唯一实现，界面读数与算法输入共用同一函数） |
| 核线、核点、核面转角 | C++ | `pgm_epipolar_*`（零依赖，见 ADR-22） |
| 特征检测、描述子、比值检验、RANSAC | C++（第二个 DLL） | `photogrammetry_cv.dll` 里调 OpenCV；主 DLL 不链接它 |

## 2 C ABI

C++ DLL 暴露纯 C ABI。

```
extern "C" int32_t pgm_resection(const pgm_resection_input* in, pgm_resection_output* out);
```

- 输入输出均为固定布局结构体，不含 STL 容器、不含指针图。
- 返回值：0 成功；非 0 为错误码，配合 `pgm_last_error()` 取描述。
- 内存：输入缓冲区由调用方持有；输出中的数组由调用方预分配，长度在输入中给出。
- C++ 异常不得跨越 ABI 边界，接口内部统一捕获并转错误码。
- **跨越 ABI 的粒度是「任务」，不是「点」。** 一次调用要么吃一个数组、要么吃一幅图，循环留在 C++ 里。逐点调用（987 个点各调一次核线距离）单看只有毫秒级，一旦进入逐像素循环就变成灾难——核线重采样 $5120^2$ 是 2600 万像素。所以 `pgm_cv_match` 一口气做完 SIFT → 比值 → 核线 → RANSAC，`C#` 只负责攒参数、收结果。判断标准很简单：**只要代码里出现「在 C# 里 for 一遍、每次调一次 C++」，就是设计错了**。

每个求解器必须附带一组**已知答案的算例**（教材数据或手工推算），残差与中误差在容差内一致才算通过。

## 3 为什么是两个 DLL

`photogrammetry.dll` 零第三方依赖，装的是"能在任何机器上重编、用合成数据验到 $10^{-14}$"的那部分；`photogrammetry_cv.dll` 链接 OpenCV，只做匹配。分开放的理由不是洁癖：演示机上 vcpkg 装不上、OpenCV 版本对不上这类事一旦发生，前者还能跑，后者只是匹配不可用（ADR-22）。

## 4 代价：C++ 信任调用方

上游一旦判错（例如判手性的三个点里有一个刺错 30 个像元、把符号翻了），C++ 不会察觉，只会照着一个镜像的输入解出一个"最不坏"的结果。所以兜底闸门**不能撤**——它们接的正是上游的错。同一个道理，匹配出来的点也必须过核线距离与前后一致性两道闸门，库给出"匹配上了"不等于"匹配对了"。

## 5 决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| ADR-14 | 算法由 C++ DLL 通过 C ABI 提供，用 MSVC 构建 | 原设计即如此，本机已装 VS2022；DLL 不依赖额外运行库，C# 侧用 P/Invoke 调用。DLL 里只放**平差计算**，边界见本文 §1 |
| ADR-18 | **C++ 只做纯计算，数据适配（判手性、换轴、认格式、统一单位）归 `Core`** | ①共线方程应当假设输入已是干净的右手系，混进 `if (isMirrored) swap(x,y)` 这类分支，会让核心算法被特定数据源的约定污染，越维护越臃肿；②判手性只要三个点、几次乘加，纳秒级，没有性能理由下沉；③读文件、认格式、统一单位本来就在 C#，判手性是同一类知识。代价：C++ 信任调用方，上游判错它察觉不到（见 §4） |
| ADR-22 | **允许引入第三方 CV 库（OpenCV，vcpkg + MSVC），但只进第二个 DLL；核线几何仍自己算** | ①老师确认可以直接用库：特征检测、描述子、比值检验、RANSAC 是成套的成熟算法，自己写只会得到更差的版本；②但 `photogrammetry.dll` 要继续**零第三方依赖**——它承载的那部分（内定向到交会、相对定向、核线）才是要在任何机器上重新编、重新验的东西，把它和 200 MB 的 OpenCV 绑在一起，等于让"能不能跑"取决于 vcpkg 的版本；③所以 OpenCV 单独编 `photogrammetry_cv.dll`，只做匹配：缺它时其他模块照常，只是匹配不可用；④核线只有几行乘加（$\mathbf n=\mathbf b\times\mathbf d_1$、$\mathbf m=R\mathbf n$），而且是匹配的**前置约束**——交给库反而多一层黑盒，自己算还能被合成像对验到 $10^{-14}$ mm |
