# 重构计划：把耦合拆掉

> 状态：**待执行**｜基线版本：2026-10
>
> 本文是唯一的重构计划与验收基线。里程碑进度见[路线图](路线图.md)，界面分层规则见[界面设计规范 §8.1](界面设计规范.md)。

---

## 0 为什么现在做

现在每加一个模块，要在 `MainWindow.xaml.cs` 里改**六处**：`Modules` 字典、`Workflows` 表、XAML 的 `RadioButton` 与面板、`ApplyModule` 的分支、`RefreshPointTable` 的分发、再写一个 `SolveXxxNow`。

模型交会（M6.5）与绝对定向（M7）落地后，这个文件大约 2500 行。那时同样的六处改动会分散在一屏以外，漏一处不报错——只会静默引用错的东西。

现状三条数字：

| | |
|---|---|
| `MainWindow.xaml.cs` | 1972 行，约 110 个成员，扛 9 类职责 |
| Snap 直接依赖窗口的 `public` 成员 | 9 个（`GcpCount`、`ControlPoints`、`CurrentProject`、`SelectGcp`、`LoadCameraFrom`、`LoadControlPointsFrom`、`BindGcpAt`、`SolveResectionNow`、`SelectModuleForTooling`） |
| UI 层代码集中度 | App 共 3236 行，其中 61% 在这一个文件 |

**这是结构问题，不是脏代码问题。** 每个方法单独看都清楚，注释解释的是「为什么」，没有 TODO / FIXME / 死代码。所以重构**不动任何算法**，只搬位置和边界。

## 5 分步计划

每一步都独立可停。任何一步做完跑完第 2 节全部命令、数字不变，才算这一步完成。

### 第 1 步：拆 partial（P0）

| | |
|---|---|
| 做什么 | `MainWindow` 按职责拆成 **7 个** partial 文件：`.cs`（外壳）、`.Library.cs`、`.Tree.cs`、`.Modules.cs`、`.Interior.cs`、`.Gcp.cs`、`.Resection.cs` |
| 影响 | 只挪代码，不删不加，不改一行逻辑；字段与构造函数全部留在 `MainWindow.xaml.cs`，副文件一律不改可见性 |
| 验证 | 编译零警告；第 2 节全部命令输出逐字一致；三张截图**逐字节一致** |
| 回滚 | `git checkout -- src/App` |
| 体量 | 半天（实际：切片 + 复验，一次完成） |

> **注意：这一步只解决「看不见」，不解决「耦合」。** 文件从 1972 行变成 7 个，但类还是同一个类，依赖关系一点没变。真正解耦在第 2、4、5 步。先把文件拆开，是为了让后面几步的 diff 能被人看懂。
>
> 计划里原写「5 个文件」，实际做的时候按 7 个拆：`影像库` 与 `模块切换` 塞回主文件会让它长到 660 行，直接突破 ≤500 的目标；而且这两块各自也是独立职责（前者第 5 步还要搬走，后者每加一个模块都要动）。
>
> 文件名保留 `MainWindow.` 前缀、但全部归入 `src/App/MainWindow/` 子文件夹。工程是 SDK 风格（没有显式 `<Compile Include>`），`.cs` 与 `.xaml` 都靠通配符递归收集，所以挪文件夹本身不需要改工程文件；唯一按路径写死的是 `App.xaml` 的 `StartupUri`，随之改成 `MainWindow/MainWindow.xaml`。验证方式就是重新出三张截图，SHA 与挪之前逐字节相同。

### 第 2 步：抽 `ResectionTask`（P1）✅

| | |
|---|---|
| 做什么 | 收集观测 → 判手性 → 换轴 → 解算 → 写回模型，整条流程搬进 `Core/Tasks/ResectionTask.cs`（`Prepare` / `Run` / `Apply` 三个入口）；窗口只留「按钮 → 调用 → 显示」 |
| 为什么 | 解算流程属于流程控制（§8.1），本来就该在 Core。搬完之后 Core 里有一个**不碰界面**的后方交会入口，M6 相对定向与 M7 绝对定向照同一个形状写 |
| 实际 | 新文件 1 个（`ResectionTask.cs` 224 行）；`MainWindow.Resection.cs` 277 → 160 行；顺手把混在里面的 `OnPreviewKeyDown` 与 `SetBusy` 归还外壳（`MainWindow.xaml.cs` 333 → 392 行） |
| 验证 | 见 §9 第 2 行 |
| 体量 | 半天 |

> **计划里的「Snap 直接调 Task」没做，因为那不是纯收益。** `--gcp` 的 M3 检查是<b>故意</b>设计成走界面流程的端到端检查：它要靠解算后刷新的点表与残差页出图。改成直接调 Task 还得另外补一次界面刷新，等于多造一个 public 入口。该做的是把 Snap 的检查拆成「不需要窗口的 Core 检查」与「一次 UI 冒烟」，那是第 3 步的活。**所以第 2 步之后 Snap 依赖窗口的成员数仍是 9，没有下降**——这一点不能含糊。
>
> 边界是这样切的：`Core` 回答「成没成、卡在哪、数值是多少」（`ResectionFailure` 枚举 + `ResectionRun`），`App` 回答「怎么排版、用什么颜色」（`FormatResection` / `FormatResidualTable`）。`Core` 里不出现任何 `Brush`、`TextBlock` 或界面文案排版。
>
> 附带修掉一个原有小 bug：解算失败后结果文字被染红，再成功时没有还原，红色会一直留着。改为成功后 `ClearValue(TextBlock.ForegroundProperty)` 回到继承色。这条不改变任何检查输出（失败→成功 的序列不在检查范围内）。

### 第 3 步：收敛 tooling 入口 ✅

| | |
|---|---|
| 做什么 | 10 个 public 成员 → 1 个（只剩构造函数）。三合一：`GcpCount` / `ControlPoints` / `CurrentProject` → 一个 `internal Project CurrentProject`；其余 7 个改 `internal`；`App.csproj` 加 `InternalsVisibleTo("Snap")`；新建 `MainWindow.Tooling.cs` 做入口登记表 |
| 为什么 | 这是个应用程序集，本来就不该有对外 API。`public` 是历史遗留，导致「哪些能改」全靠记性 |
| 判据 | **改了判据，见下**：`MainWindow` 的 public 成员 = 1（构造函数）；Snap 用到的每个窗口成员都能在 `Tooling.cs` 的表里查到 |
| 验证 | 见 §9 第 3 行 |
| 体量 | 半天 |

> **原判据「Snap 直接调用的窗口成员 ≤ 3」测得是错的东西。**动手前核实发现：`--selftest`、`--control`、`--probe`、`--fiducial` 四条检查**本来就不碰窗口**——`ControlCheck(string?, string)` 自己造 `Project` / `ImageItem`，直接调 `NativeAlgorithms`。真正用窗口的只有渲染路径与 M3，而 M3 的全部意义就是走界面链路（它要断言「解算后点表刷新了、框标方式关了、刺点模式开了」）。所以没有一条检查需要搬。收敛不等于搬家：**该做的是把开口收窄并登记清楚**，不是把 8 个方法体挪到另一个文件里——它们要碰 `x:Name` 字段和私有状态，挪出来只会把两份代码拉远。
>
> 也不物理搬方法体，只改可见性 + 一张登记表：搬的收益只有「好找」，代价是 8 段代码挪位的 diff 风险。表给的是同一份地图。`Tooling.cs` 里写了一句留给以后的规则：**加新入口之前先问——界面上的按钮能不能直接调私有处理器？能，就别加。**
>
> 顺带治掉一个 Snap 的老毛病（见 §2.3）：带影像的截图里，状态栏右端的光标读数据跟着**物理鼠标**位置走，同一份代码 6 次跑出 3 种哈希。截图前把 `StatusCursor` 复位成「—」，现在 4/4 完全一致。用 `FindName` 取的，没给窗口新增任何入口。

### 第 4 步：点表去重（P2）✅

| | |
|---|---|
| 做什么 | 两张点表的刷新收敛成一个 `RefillTable<TRow>(grid, rows, 恢复条件)`；格式串搬进行类型（`GcpRow.From` / `FiducialRow.From`）；`FiducialRow` 从 `MainWindow.Gcp.cs` 归位回 `MainWindow.Interior.cs`（框标表的行定义原先躺在控制点文件里） |
| 为什么 | 刷新是六步：判空 → 拍下选中行 → 逐行格式化 → 换数据源 → 写摘要 → 恢复选中。两张表只有「建行」与「摘要文案」不同，其余四步逐字雷同；而格式化住在刷新方法里，行对象只是个空壳 |
| 实际 | **行数几乎没变**：两文件代码行 813 → 816（+3），总行 500+520 → 514+542（+36，全部是新加的注释） |
| 验证 | 见 §9 第 4 行 |
| 体量 | 半天 |

> **计划里写的「两个方法各减约 30 行」是错的。**去重删掉的只是「换数据源 + 恢复选中」那一对（约 25 行），格式串并没有消失——它从刷新方法搬进了 `From` 工厂，一行不少。这一步的收益在**结构**不在行数：格式串从此只有一个所有者（加一列、改小数位只动一个文件），两张表共用同一段恢复选中逻辑，不会再出现「这张改了、那张忘了」。
>
> 一个坑写进了 `RefillTable` 的参数注释：恢复选中的判断必须闭包一个**局部快照**。换 `ItemsSource` 会触发 `SelectionChanged`，现读 `_activeGcpId` / `_activeFiducialId` 就会踩到换源后的新状态。现在的两个处理器在选中为空时会提前返回、恰好不写字段，但依赖这个巧合太脆。
>
> 验证方式补了一条：原基线**没有一条看框标表**（默认停在「诊断」页，点表根本没显示出来），所以加了 `--module 内定向 --camera … --tab 点表`，并先用 worktree 拉 `HEAD` 出「改前」的同一张图来比。

### 第 5 步：服务外移（P3）✅

| | |
|---|---|

> **为什么这一步要额外的验证。**封送布局错一个字段（类型、顺序、`SizeConst`）不会编译报错，只会静默算错——前面五步那套「日志逐字比、截图逐字节比」能抓到，但抓到的时候已经是一堆数字对不上了，很难定位。

>
> 踩到一个坑值得记：`[StructLayout]` **不是**保留在元数据里的自定义特性，`GetCustomAttribute<StructLayoutAttribute>()` 拿到的是 null，第一版 `--abi` 因此报「struct 0 个」。它落在 `TypeAttributes` 的布局标志上，要通过 `Type.StructLayoutAttribute` 读。
>
> 还抓到一处自己的疏漏：切片从 186 行开始时，178 行的 `Library` 常量没被排除，于是它在两个文件里各留了一份。`NativeAlgorithms` 里那份已经没人用（编译不报错，`const` 不产生未使用警告），是复查残留引用时才发现的。

## 6 顺序与依赖

```
第 0 步 锁基线 ──> 第 1 步 拆 partial ──> 第 2 步 抽 ResectionTask ──> 第 3 步 收敛 tooling
                                              │
                                              └──> 第 4 步 点表去重 ──> 第 5 步 服务外移 ──> 第 6 步 ABI 拆分
```

- 第 1 步必须在最前：它不改行为，却是后面所有 diff 可读的前提。
- 第 2 步是**唯一的实质解耦**，其余是配套。
- 第 4–6 步彼此独立，可以按剩余时间挑着做。

## 7 不做什么（防止范围膨胀）

| 不做 | 理由 |
|---|---|
| 不碰任何算法与数值（DLL、`NativeAlgorithms` 里的数学、判手性规则） | 已经过七段验收与真实数据验证，动它只有风险没有收益 |
| 不改 `.pht` 结构 | 第一条路线读写无损；模型/像对的字段等 M6.5/M7 有产物了再一次加 |
| 不引入 MVVM 框架、DI 容器、`ReactiveUI` 之类 | 课程项目的收益不抵引入的复杂度。目标是「按职责分文件」，不是「上架构」 |
| 不改界面视觉与交互 | 重构期间界面必须保持一模一样，否则截图基线失效 |
| 不补单元测试 | 现有 Snap 六项检查已覆盖数值与流程。真要补，等结构稳定后单独一轮 |
