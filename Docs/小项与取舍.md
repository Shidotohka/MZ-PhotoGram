## 2 需要解释的四条

### 2.1 X-02 为什么不存模型点（而不是"存得更聪明些"）

模型点不是"少量成果"，而是一次解算的**中间产物**，而且数量级完全不同：

| 谁产生 | 一次多少点 | 谁消费 |
|---|---|---|
| 相对定向（同名点） | 十几到几千 | 模型交会 |
| 模型交会（控制点） | 手指头数得过来 | 绝对定向 |
| 稠密匹配（未做） | $10^6$–$10^7$ | 点云视图 |

只要有一格是 $10^6$，`.pht` 就不再是"能 diff、能手改、能人读"的索引文件，而变成半个点云文件。
真要做稠密那一档，正确形态是**独立的 `.ply`/`.xyz` + 工程里一条索引**，而不是把二进制塞进 JSON。
现在这张表既没人写也没人读，留着只是误导——所以删容器，不删能力：模型交会与绝对定向照常出数，成果在结果窗口看。

### 2.2 X-01 为什么最后没用现成的缓存库

`Microsoft.Extensions.Caching.Memory` 有 `SizeLimit`，看着正合适，包也装上了。两条实测把它挡在门外：

| 实测 | 结果 | 后果 |
|---|---|---|
| 往"刚好满"的缓存里再加一张 | 被淘汰的是**刚加的那张**（压缩顺序「后进来的先出」） | 用户每打开一张新图，缓存就把它扔掉——命中率归零，等于没缓存 |
| 用淘汰回调记账占用 | 回调不保证同步执行，`Bytes` 滞后一拍 | "腾到装得下"的循环会按旧数字继续腾，多淘汰一张 |

两条都能绕着走（自己记顺序 + 自己记账），可那就已经不是"用库"了：库剩下的只是存储，而存储用 `Dictionary` 本来就有。
所以退回自写 40 行，把这两条实测写成 `Snap --cache` 的断言——**第 4 条就是那道防线的守门人**：
谁哪天想换回库，它先红。

### 2.3 X-05 为什么不加自动弃点

1. **点数不够用**。绝对定向的最低配置是 3 个控制点；3 点上弃 1 个，方程数与未知数相等（7 个方程 7 个未知数），残差恒为 0，解不出任何判据。
2. **它会掩盖几何问题**。11-07 那次真实实验（`Data/real/实验_相对绝对.pht`）的四个控制点不一致值是 8.48 / 1.00 / 6.93 / 9.69 m，**符号正负交替**——这不是"某一个点刺错了"，是 $H/B=8.86$ 时手工刺点误差被放大，弃掉"最大的那个"只会让 rms 好看、让结论更错。
3. **现在的做法是"让你看见"**：结果窗口把平面与高程拆成两行，σ₀ 折成像元与 VL-13 的 10 px 判据并排。看见 5.30 px 的人会去查数据，被自动弃点伺候过的人不会。

### 2.4 X-06 更正：量化发生在 ABI 边界，不在存储层

此前把它记成"存储层把内核的小数截成整数"，这是错的。整条链只有一处把小数变成整数：

```
匹配 / 点选给的是 double  ←  Coordinates.cs:100   new ImagePixel((int)Math.Round(i), (int)Math.Round(j))
                                                        ↓
                                          ImagePixel(int I, int J)  ← C ABI 的像元口径
                                                        ↓
                                     ImagePoint.PixelX/PixelY 也是 int，跟着它走
```

所以不是某一层忘了转换，而是**整个 C ABI 就以整像元为单位**：$i,j$ 是整数，核线重采样、交会、残差都按整数进。
代价是均匀量化，标准差 $0.5/\sqrt{3}\approx0.29$ px——比手工取点（0.2–0.7 px）还小一档，而且对**所有点**一致，不会造成系统偏差。
改成 double 要动 C ABI 的每个结构体与全部原生函数签名，收益是"自动匹配的点从 0.29 px 精度变成 0.1 px"，而那批点目前不参与任何验收项。**不改**，把口径写清即可。
